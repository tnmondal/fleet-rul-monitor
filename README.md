# Fleet RUL Monitor — Predictive Maintenance for Turbofan Engines

Predicts **Remaining Useful Life (RUL)** of jet engines from multivariate
sensor telemetry, using the NASA C-MAPSS dataset schema. Full stack: ML
pipeline, FastAPI backend, React dashboard.

```
pm/
├── ml/            data generation, feature engineering, model training
├── backend/       FastAPI inference service
└── frontend/      React + Vite dashboard
```

## About the dataset

This was built in a sandboxed environment with no internet access, so
`ml/data/raw/` contains **synthetic data** generated by
`ml/data/generate_cmapss_like_data.py` — it matches the real NASA C-MAPSS
schema exactly (same 26 columns: `unit_number`, `time_in_cycles`, 3
operating settings, 21 sensors) and the same statistical shape (piecewise
degradation curves, per-engine noise, multiple operating regimes).

**To use the real dataset:**
1. Download `train_FD001.txt`, `test_FD001.txt`, `RUL_FD001.txt` from
   [Kaggle: NASA C-MAPSS](https://www.kaggle.com/datasets/behrad3d/nasa-cmaps)
   (mirrors the official [NASA Prognostics Data Repository](https://data.nasa.gov/dataset/C-MAPSS-Jet-Engine-Simulated-Data/ff5v-kuh6))
2. Replace the files in `ml/data/raw/`
3. Re-run `python ml/src/train.py` and `python ml/src/export_sample_fleet.py`

Everything downstream — feature engineering, training, API, frontend —
works unmodified either way, because the schema is identical.

## Quickstart

### 1. ML pipeline

```bash
cd ml
python -m venv venv && source venv/bin/activate   # optional but recommended
pip install -r requirements.txt

python data/generate_cmapss_like_data.py   # or drop in the real dataset
python src/train.py                        # trains & compares 3 models, saves best
python src/export_sample_fleet.py           # exports demo data for the frontend
```

`train.py` compares Linear Regression, Random Forest, and Gradient
Boosting using **GroupKFold cross-validation** (so no engine's cycles leak
across train/val splits) and selects the best model by the official
**NASA asymmetric scoring function** (`src/scoring.py`), which penalizes
late predictions — i.e. the model being overconfident an engine still has
life left — far more heavily than early ones. This mirrors the real cost
asymmetry in maintenance scheduling.

Artifacts land in `ml/models/`: `rul_model.joblib`, `scaler.joblib`,
`metadata.json` (feature list, CV/test metrics, feature importances).

Explore `ml/notebooks/01_eda.ipynb` for the sensor-selection rationale
and RUL-capping reasoning behind the pipeline.

**Upgrading the model:** if you have internet access, `pip install
xgboost` and swap `GradientBoostingRegressor` in `train.py` for
`xgboost.XGBRegressor` — same `.fit`/`.predict` interface, typically a
meaningful accuracy gain over sklearn's GBM on this kind of tabular data.

### 2. Backend

```bash
cd backend
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

Requires `ml/models/*.joblib` and `ml/data/sample_fleet.json` to exist
(from step 1). Endpoints:

- `GET /api/health`
- `GET /api/model-info` — best model name, cross-val/test metrics, top features
- `GET /api/sample-fleet` — demo engine trajectories for the frontend
- `POST /api/predict` — send recent sensor readings for one engine, get back
  predicted RUL + risk level

Interactive docs at `http://localhost:8000/docs`.

### 3. Frontend

```bash
cd frontend
npm install
npm run dev
```

Opens at `http://localhost:5173`. Vite proxies `/api/*` to the backend
on `:8000` (see `vite.config.js`) — run the backend first.

## Design notes

- **Feature engineering**: rolling mean/std (5-cycle window) per sensor,
  on top of raw readings — captures trend, not just instantaneous value,
  which is what actually drives RUL predictability in this kind of data.
- **Sensor selection**: 7 of 21 sensors are dropped as near-constant /
  uninformative across engine life (see `DROP_SENSORS` in
  `ml/src/features.py`, justified in the EDA notebook) rather than fed
  in blindly.
- **RUL capping**: training labels are capped at 130 cycles — a standard
  CMAPSS trick, since RUL isn't meaningfully predictable from sensors
  alone while an engine is still deep in its healthy phase.
- **Evaluation protocol**: test-set predictions are made from only the
  *last observed cycle* of a truncated trajectory, exactly matching how
  the real C-MAPSS test set is designed — you don't get to see the future.
- **Risk bands**: `<20` predicted cycles = critical, `<50` = warning,
  else healthy. Adjust thresholds in `backend/app/inference.py` if your
  maintenance windows differ.

## Extending this project

- Swap in the real C-MAPSS dataset (see above) and compare metrics —
  real sensor noise is messier than the synthetic data here, so tree
  models will likely pull ahead of linear regression.
- Add an LSTM/1D-CNN model trained on raw windowed sequences instead of
  hand-engineered rolling stats, and compare against the tabular baselines.
- Try the other C-MAPSS sub-datasets (FD002–FD004), which introduce
  multiple operating conditions and fault modes — a good test of whether
  your feature engineering generalizes.
- Persist predictions to a database and add a history view instead of
  computing on-demand every page load.
